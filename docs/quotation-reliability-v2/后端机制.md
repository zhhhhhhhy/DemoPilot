# 可追问的后端设计

项目目标是让销售需求生成的演示应用可验收、可返工、可追溯。报价只是具体业务载体。旧版已有意图询问、异步运行和展示页面；本次新增独立的报价 Core 与验收发布台，尚未把新 Core 接到旧 Vue 询问表单。

## 为什么要有外层循环

Codex CLI 是当前代码执行内核，`HarnessAdapter` 是替换边界。父级提供目标、完整业务规则、只读测试数据位置、允许写入目录和验收命令。CLI 生成或修改页面；父级核对写入范围并执行公开业务检查，将具体失败返回同一 Core。每个版本最多三次 CLI 调用，每次最多300秒。通过才能发布；耗尽预算则隐藏并保留失败。

这里的“内部返工”指整个 Core 循环内部，不要求 Codex 在一次 CLI 进程内完成全部修复。最终独立检查发生在所有任务终态之后，不回传检查结果，不人工改页面后换分。

## 金额与流程如何验证

`quotation_contract.py` 用 Python Decimal 计算金额，并维护报价状态、角色、记录、审批版本与操作历史。验收编译器把操作序列转成逐步可见结果：输入什么、谁点击什么、是否允许、页面应该显示什么。`quotation_browser.py` 通过本机无头 Chromium 实际填表、切换角色、点击和刷新，再比较可见结果。生成应用使用 JavaScript，两份实现相互独立；二者仍共享同一业务定义，所以另外保留人工可核算金额例子与受控故障检验。

v2增加运费后，既检查新配送方式，也重新执行原有报价、审批、修改失效和记录隔离路径。“新增功能通过”与“原功能没有退化”分别统计。

## 如何防止旧任务覆盖新需求

需求版本只能单调前进，同版本的业务定义不可改写。SQLite 通过 `UNIQUE(project, revision)` 与 `BEGIN IMMEDIATE` 保证一个版本只有一个任务认领。随机所有权令牌绑定后续写入；它没有过期时间和续租机制，不能包装成分布式租约系统。

验收记录绑定任务、产物 SHA-256 与完整报告。发布先把文件复制到独立暂存目录并校验哈希，再在数据库事务内重新核对最新需求版本、任务所有权、通过的检查记录与产物哈希，最后提交发布指针。旧版本晚返回、失败检查、产物被改、其他任务冒领，都会被拒绝。重复提交同一已发布结果返回原记录。

数据库是发布状态的依据。文件先落盘而事务未提交，只会留下未引用的包；这个设计没有宣称分布式事务或跨机器高可用。文件系统包通过哈希与发布入口保护，并非操作系统不可写存储。

## 为什么页面和脚本也要固定版本

若页面入口和 `app.js` 都指向“当前版本”，浏览器先拿到v1 HTML、发布指针再切到v2，就可能读取v2脚本。入口因此跳转到 `/accepted/项目/版本/产物哈希/index.html`，相对 CSS/JS 也保持同一个版本。历史已验收包可以显式访问；默认项目入口只解析当前需求的已验收版本。

## 如何留下失败证据

每次调用保存实际 prompt、CLI JSONL 对话、标准错误、命令执行事件、检查报告及候选哈希。每个版本另存终态候选，避免后续改版覆盖旧版。实验先冻结代码和输入，再做生成；所有终态之后才运行另一组浏览器路径。发布成功但最终业务检查失败，仍计为失败；中途超时后自行修复成功，只计内部返工。

浏览器诊断日志属于工具运行输出，应该写入工具证据目录。不能因为日志名叫 `debug.log` 就放宽任意越界写入的限制。电脑睡眠等宿主异常也单独记录，不能解释为模型业务能力变化。

## 面试边界

当前是单机实验系统，使用合成配置与公开业务来源；没有生产用户、销售收入、人工工时或千级并发指标。写入范围由 CLI workspace 策略、prompt约束和完整性检查共同约束；没有证明所有操作系统读取都被隔离。新旧链路、受控故障和真实生成对照各有独立证据，不合并成一个成功率。
