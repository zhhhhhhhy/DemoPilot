# 面试讲稿与追问

## 30秒介绍

我做了 DemoPilot，一个把销售需求变成可操作演示的 Agent 系统。我重点解决的是“模型说完成了，但业务可能没做对”这个问题：把报价计算、角色审批和修改失效规则变成可执行验收，让 Codex 在预算内生成、测试和返工，通过后才发布。后端再把需求版本、任务所有权和产物哈希绑定，避免旧任务覆盖新结果、页面和脚本跨版本混用。为检验效果，我构建了100个业务组合，并用完整信息对照和真实浏览器验收保留结果。

## 两分钟介绍

项目面向售前演示。销售通常先说一句需求，系统追问缺失规则，整理后交给代码 Agent。最初我想证明意图模块有用，后来发现直接比较一句话和询问后的完整需求，会同时改变信息量和处理方式。所以我追加了“完整规则直接交给 Core”的对照，确认已有证据主要支持获取缺失信息，不能说结构化意图本身让模型更聪明。

接下来我把重点转到工程交付：即使规则给全，生成的页面也需要业务验收，改需求后还要保住旧功能。我选择报价场景，因为金额可以独立核算，审批又有多角色和状态约束。用公开规则组合出10类流程、100个定价与流程组合，每个应用先生成初版，再增加配送需求。验收不是只看页面或代码，而是用另一份 Decimal 和状态机实现生成预期，再让 Chromium 实际操作页面。

Core 通过可插拔 Harness 调用 Codex CLI。每个版本最多三次调用，父级每次检查实际业务行为；有问题就把具体输入和差异返回同一循环，没通过就保持隐藏。最终评测另外运行，结果不回传模型，避免测完再改成满分。

发布端我处理了两种竞态。第一种是新需求已经到了，旧任务才完成：提交时必须重查最新版本、任务所有权和验收对应的产物哈希。第二种是浏览器拿到旧 HTML 后又请求到新 JS：页面入口跳转到固定版本及哈希的资源包。完整对照结果和故障注入结果分别存档，具体数字见[结果与贡献](结果与贡献.md)，不会把合成组合说成真实客户，也不会把受控故障检验说成自然模型准确率提升。

## 常见追问

**是不是只是包了一层 CLI？** CLI负责写代码，我的设计负责规定什么结果算完成、怎么在预算内返工、什么结果可以发布，以及如何追溯失败。可执行业务契约、版本一致性和公平评测是这个项目的主要工程内容。

**已经接入多个Harness了吗？** 目前真实验证的是Codex CLI适配器，统一build和acceptance接口为替换内核预留边界。可以说可替换接口设计，不能说已经完成第二种框架的真实兼容测试。

**返工是谁要求的？** 产品 Core 包含 CLI 适配器和父级循环。父级业务检查将错误返回同一 Core，修复后重测。它属于 Core 内部迭代。所有任务完成后的最终浏览器检查属于离线评测，不帮助模型返工；最终仍错就计失败。

**为什么不用一个大模型 Reviewer？** 金额和审批规则能明确计算，优先用可重复的程序检查，避免两次模型都认可同一个错误。程序检查也可能写错，所以另有人工可核算例子、受控错误检验和不同输入的最终路径。审美、开放式业务理解等仍不在这些确定性规则的证明范围内。

**怎么确认新增功能没有把旧功能弄坏？** v2在同一个工作区修改，保留v1的所有原有流程路径，再加配送路径。分别记录新功能成功与原有功能回归，而不是只测试新增按钮。

**并发控制具体做了什么？** 数据库对项目和需求版本建立唯一约束，在事务中认领任务；发布再次核对最新需求版本、所有权令牌、验收记录和产物哈希。验证中有8个并发认领请求，只有一个获得所有权。这是单机 SQLite 机制，没有宣称分布式锁、到期续租或高并发吞吐。

**验收通过后页面又被改了怎么办？** 验收记录绑定精确哈希。复制到发布包后重算哈希，发布事务再核对；读取发布资源也校验包。这里的不可变是应用约束和篡改检测，不是文件系统永远不能被写。

**100条数据够证明模型能力吗？** 100是10种流程和10种定价的组合，独立应用组只有10个，其中3组开发、7组主评测。它足够作为声明规则内的工程回归集，不足以宣称广泛用户成功率。重复执行的浏览器路径也不是独立客户样本。

**两组都通过，业务门禁有什么用？** 这说明强模型配完整规则和自测在本集上已经做得很好，不能硬说最终准确率提升。门禁的已验证作用要看受控错误能否被拒绝、错误候选是否保持隐藏、修复后才发布，以及竞态下是否仍发布正确版本。这些与自然任务成功率分开报告。

**有没有真实用户收益？** 本阶段没有真实销售用户和生产收益数据。已有的是公开来源、可运行链路、完整对照记录和受控故障证据，下一阶段才需要接入真实销售反馈。

**哪些是你做的，哪些是 AI 做的？** 我负责问题拆解、意图与验收契约、对照设计、失败归因及发布约束，使用 Codex 辅助实现和测试。面试时应能解释关键代码和取舍，不把 AI 辅助项目描述成全部手写。

## 演示顺序

1. 打开本地验收发布台，进入一个已验收报价应用。
2. 改数量与配送方式，观察金额及审批路径；审批后再修改，验证旧批准失效。
3. 展示一次受控错误的“隐藏→业务拒绝→真实CLI修复→发布”证据。
4. 展示一个旧任务被拒绝和固定版本资源的测试，最后打开对照结果解释指标边界。

本次新 Core 和发布台是独立实验模块，旧 Vue 销售询问页面尚未接入这个新增后端。演示时说明这一点。
