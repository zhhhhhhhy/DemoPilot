# 报价可靠性升级 v2

目标是把“会生成一个页面”升级成“复杂业务正确才发布、需求变化后旧功能仍正确”。本次所有生成都交给真实 Codex CLI，外层仅提供完整目标、限定写入范围、确定性验收反馈与发布状态。

## 数据与统计单位

10类应用各包含10种定价规则，得到100个业务组合。它们是100个组合测试，不是100个独立客户或100个独立应用。按整个工作流分组：前3类用于调试，后7类预先冻结后评测；结果同时报告应用全通过数和组合通过数，不能用组合数量掩盖应用数量。

每个应用先从零生成v1，再在同一工作区接收v2需求：增加自提/标准配送/加急配送，运费在优惠与税后整单收一次并参与审批路由；旧的自提报价功能必须完整保留。变化前后都覆盖全部100个组合。

## 对照

两组收到相同完整业务规则、相同测试数据与可执行公开检查方法，使用同一个模型、推理设置和每版本最多3次CLI调用、每次300秒的上限。普通组可自行测试返工，发布前采用结构检查；可靠性组在相同调用预算内加入业务检查，错误反馈回到同一Core循环。比较的变量是确定性门禁与回归反馈，而非是否给了完整业务信息。调试预试用180秒发现规划和完整实现耗时不足；正式两组统一300秒，不将预试计入提升。旧实验与本次目标和循环不同，不跨实验比较。

两组使用同一版本安全发布机制；另外用受控并发及故障场景验证它能阻止旧版本、被篡改产物与重复请求。该性质测试单列，不算模型准确率或独立需求。

## 独立评测

每个应用都有随完整规则一同提供的公开操作序列，主评测应用同样可以自测。最终评分使用事先冻结的另一组输入、边界、角色、记录切换与状态变化路径，全部终态后运行，评测结果不返给Core，不据此修理或覆盖原分数。若某应用未生成成功，同样计入分母，不丢弃失败。结果分别统计完整业务通过、错误发布、旧功能回归、内部返工及真实CLI调用。回归指声明路径中的旧行为保持，未测浏览器已有真实数据跨代码版本迁移。

## 边界

公开ERPNext文档及用户问题提供业务模式，商品、金额、身份和组合由本项目合成；不宣称真实客户数据或ERPNext当前仍存在历史问题。浏览器在本机无头Chromium执行，不是已登录的用户浏览器。新后端为可运行的独立v2模块，不偷换旧实验运行时；是否接入旧前端必须在最终报告明确。
