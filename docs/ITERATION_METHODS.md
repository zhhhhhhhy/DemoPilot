# Engineering iterations

## IT-001: Move DemoPilot to an explicit intent -> acceptance -> result loop
- Date: 2026-10-05
- Status: implemented; live full-run follow-up remains bounded by model latency
- Problem and user impact: The current DemoPilot already freezes interaction contracts and records browser evidence, but its user-facing flow starts from a dense brief form and defaults to a remote provider. The article's most reusable idea—make the intent, the acceptance standard, and the result explicit—needs to be visible in the product. The local authenticated Codex CLI also needs to become a first-class iteration provider.
- Acceptance condition: A user can express boundary, priority, acceptance criteria, and constraints, confirm a one-page intent statement, choose Codex CLI, and submit. The run stores the intent statement, uses `codex exec --json` for agent calls, keeps the existing deterministic/browser/reviewer gates, and exposes result evidence and remaining human gates in the delivery view. Missing Codex auth or invalid structured output fails closed without silently switching providers.
- Proposed method: Add a bounded `codex_cli` provider around the local authenticated CLI; add backward-compatible intent fields and a deterministic intent statement; add confirmation and intent/acceptance/result cards to the Vue workflow; add unit, API, UI, and smoke checks.
- Work performed: Added `DemoRequest` intent dimensions and a durable `intent_statement`; added a fail-closed Codex CLI provider using `codex exec --ephemeral --sandbox read-only --json` with a strict schema wrapper, serialized local CLI calls, timeout/child-process cleanup, and no silent Mock fallback; added confirmation and intent/acceptance/result evidence cards to the Vue workflow; added API, provider, model, and UI regression tests; documented CLI configuration in `.env.example` and `README.md`.
- Observed result: Ruff passed; 47 backend tests passed; ESLint passed; 4 frontend tests passed; frontend production build passed; Mock API end-to-end delivery passed with intent fields persisted; Codex CLI 0.160.0 returned a non-empty structured Brief result using the saved ChatGPT login; a short-timeout process-cleanup check failed closed without orphaned CLI output. Full live Codex runs reached the real Agent Team but exceeded the 180-second per-agent guard during live service latency; a 600-second attempt reached the design stage before being stopped to avoid an unbounded account run, so browser/Reviewer evidence is not claimed for that provider run.
- Evidence: `docs/engineering/preflight-2026-10-05-02.json`, `docs/engineering/allocation-2026-10-05.json`, `docs/engineering/preflight-2026-10-05-03.json`, `backend/tests/test_codex_cli_provider.py`, `backend/tests/test_intent_statement.py`, `frontend/src/App.spec.ts`, and the final command outputs recorded in the task log.
- Remaining limitation or cause: No project `.env` or DeepSeek key is configured. Codex CLI authentication and Brief-level structured output are verified; a full nine-node live run remains sensitive to model-service latency and should be rerun with a deliberate higher timeout before treating its browser/Reviewer result as representative.
- Next method for this problem: Keep the deterministic Mock and local CLI smoke gates in CI, expose the configured timeout as an operator setting, and run one full Codex CLI acceptance task with a higher timeout when live model latency is acceptable.

The user explicitly required a real end-to-end debug path and allowed assisted intent entry.
- Acceptance condition: Use the same browser-submitted synthetic intent and the `codex_cli` provider; preserve failed attempts; make every live CLI call observable without persisting model text; resume from checkpoints; require the existing approval, deterministic validation, Chromium interaction checks, and independent Reviewer before claiming completion. Add a delivery-room debug trace and preserve the original timeout/parse/validation histories.

- Debug boundary: the trace stores process/event types, safe thread ID, status, elapsed seconds, stdout byte count, usage counters and errors; it does not store model reasoning text, customer input or credentials. The final Reviewer still distinguishes real browser interactions from simulated business data and records the static-demo boundary.

## IT-003: Tiered Agent Core evaluation set with public invoice fixtures
- Date: 2026-10-05
- Status: implemented; one post-correction real case reached Chromium, but the full 20-case real run remains pending
- Problem and user impact: Two hand-picked demos were too small to tell whether the Agent Core could generate simple, medium, and hard workflows. The evaluation needed explicit intent, goal, flow, and evaluation method fields, a reproducible browser contract, and public input material without leaking a hidden answer file to Codex CLI.
- Acceptance condition: Freeze 20 cases with 10 simple, 5 medium, and 5 hard cases; define difficulty from business phases (simple 1–2, medium 3–5, hard 6+ with branches/errors/audit); collect ten checksum-pinned public synthetic invoices; send the explicit prompt contract through the real `codex_cli` provider; run Chromium and Reviewer gates; preserve every failed result and keep the OCR gold separate.
- Method: Add `evaluation_mode=core_generation` and explicit `evaluation_*` request fields; seed the authored contract directly so the real CLI path focuses on Builder -> deterministic gates -> Runner/Chromium -> Reviewer; redact browser assertions from Codex prompts; copy fixtures into each run with SHA-256 and JPEG validation; execute authored browser paths in Chromium; keep Mock only for offline regression. The invoice path checks visible completion, structured result labels, and switching between two inputs, rather than hidden OCR values.
- Work performed: Added `evaluation_sets/codex-cli-v1/cases.json`, `invoice-manifest.json`, `invoice-gold.json`, ten local JPG fixtures, the collection and runner scripts, core-generation contract compilation, asset mounting, prompt redaction, browser contract execution, and static selector checks. Added schema, intent, prompt-boundary, and interaction-contract tests.
- Observed result: 20-case dry-run passed with exact 10/5/5 counts; targeted post-fix tests passed; the full suite is rerun before commit. Real run `d348ad3b567c` failed closed after a Builder JSON parse failure. After the frozen-contract integration, run `4ed1d4a4de5d` reached Runner, Chromium, and Reviewer with 11 real CLI calls and 2 revisions, but failed the quality gate because the generated invoice mapping did not satisfy the first gold-bound contract and the original source-reference check was too strict. Retry `ee9996f72e96` failed closed on an invalid structured Builder response before Runner; retry `53ffc4db553d` reached Runner, Chromium, and Reviewer and exposed incomplete asset references. Core-only run `b7ea89a5f618` reached Reviewer but timed out on the old 180-second guard. Post-fix run `c44966743537` used the direct Core Builder path, reached Chromium on revision 1, and recorded real browser evidence: story advancement and navigation highlighting passed, while the invoice journey failed because the generated controls were hidden and image paths were missing. Reviewer returned `revise` (22/100); the run was correctly recorded as failed after four revisions. These are failures in the denominator, not passes.
- Evidence: `evaluation_sets/codex-cli-v1/README.md`, `evaluation_sets/codex-cli-v1/cases.json`, `evaluation_sets/codex-cli-v1/invoice-manifest.json`, `evaluation_sets/codex-cli-v1/invoice-gold.json`, `scripts/run_codex_cli_eval_set.py`, `docs/engineering/allocation-2026-10-05-codex-eval-set.json`, `docs/engineering/preflight-2026-10-05-codex-eval-set.json`, `docs/engineering/preflight-2026-10-05-core-calibration.json`, `evaluation_sets/codex-cli-v1/results/real-smoke-simple-invoice-core-browser-20261005.json`, and `.data/runs/c44966743537/`.
- Remaining limitation: The dataset and real path are in place, and Chromium has been exercised by the real path, but a complete 20-case CLI score has not been run. The remaining score must report per-tier terminal results and keep browser failures, CLI timeouts, and Reviewer decisions separate from any pass rate.
- Next method for this problem: Use the corrected fixture subdirectory mounting and 300-second per-agent default, rerun the simple invoice case until its authored controls are visible and resources load, then execute simple, medium, and hard tiers sequentially with a fixed timeout and a result manifest. Publish per-tier pass rates only after every selected case has a terminal result.
