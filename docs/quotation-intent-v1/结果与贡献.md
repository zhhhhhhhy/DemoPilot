# 报价场景：结果与个人贡献

> 后续已追加“不经意图模块、完整规则直接给Core”的C组。结果支持补齐业务信息，未显示意图整理带来额外最终通过收益；最新贡献边界见[三组报告](../quotation-information-ablation-v1/结果与简历贡献.md)。下方保留原A/B记录，数字未改。

本轮结论：**观察到最终交付提升**。未参与调试的六条需求，直接生成通过 **1/6**，先询问再生成通过 **5/6**，本轮多通过 **4** 条，差 **66.7 个百分点**。

这里的通过是：原任务交付成功，且所有指定商品、客户、数量、日期、金额、税额、赠品和错误输入检查全部通过。以最终交付和独立业务检查为准。Core内部报错后自行修好只记返工，最终结果仍按同一规则评分。

## 原先要解决什么

销售可能只说一句“做一个报价演示”，却没有说清优惠门槛、客户适用范围或规则冲突时怎么办。直接生成容易做出能运行、但不符合销售真正要求的页面。项目目标是先获得必要规则，再交给同一个生成内核持续实现、测试与修复。

## 你的贡献是什么

1. **设计需求到交付的流程。** 将原始话术、模型实际提出的问题、固定的模拟销售回答、整理后的目标和Builder输入分别保存；只把问到的业务事实交给Builder，同时保留原始回答，避免信息在整理时丢失。
2. **建立能判断对错的验收。** 将公开报价规则变成明确配置和可执行检查，覆盖边界、规则冲突、税额、买赠及非法输入；用独立的数值计算与真实浏览器读取结果，识别“已经生成但没有实现要求”的情况。
3. **把效果比较做成可复核实验。** 固定四条调试题、六条新题、模型、生成预算和评分；保存失败、日志和耗时，保留信息充分的任务来检查多余询问，不靠修改新题答案制造提升。

Codex CLI提供基础理解和写代码能力；上游项目及AI辅助实现应如实说明。你的可归因贡献是上述需求获取、上下文交付、执行与验收设计，不能把基础模型能力说成个人算法发明。

评分后诊断与原始评分分开保存，没有给Core反馈、重写结果或替换失败项。详见[测量说明](measurement-notes.md)。

## 怎样理解这个提升

两组使用同一个Core、同一组普通数据和同样的返工预算。询问组额外获得了实际询问到的销售配置，并将这些事实与整理后的目标交给Core。因此可归因于“需求获取与可靠传递”这一整套方法，不能单独归功于提示词措辞。

六条新题中，只有询问组通过的有4条，只有直接组通过的有0条。按题配对的双侧精确检验值为0.12500；它只作小样本诊断，不能把上百条相关操作当作上百个独立客户，也不能从单次运行推断稳定的总体收益。

十条需求来自四份同一产品体系的官方业务文档；具体样例和销售回答是构造的。四条调试题不混入主结果，保留题没有在评分后修复或重写成绩。意图问答在独立实验runner运行，产品前端尚未接入真人问答会话。真人销售满意度、制作工时节约、客户转化率均未测量。

## 可以怎样用于面试

项目介绍应围绕：一句话需求缺少关键业务规则时，如何获得这些规则、可靠交给生成Agent，并通过独立验收验证最终交付。说明为什么仅测试页面能否打开会误判完成，再展示一组原始话术、追问回答、生成文件和浏览器检查。

可核实的结果表述：“基于公开报价业务规则构建10条评测需求，固定4条开发与6条保留测试；在同模型、同生成预算下，完整业务通过从1/6变为5/6，代价为外层CLI调用从14次变为25次。”这是公开规则和模拟销售回答上的单次小样本结果，尚不代表真实销售收益。
