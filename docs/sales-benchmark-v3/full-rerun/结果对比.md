# 修复版本：原20题完整复验结果

**结论：3/20（15%）→19/20（95%），多交付16条，提高80个百分点。** 原始3/20与选定三题0/3→3/3均保留，本次是另开批次完整重跑，不是把三题回归拼进旧成绩。

## 本次究竟证明了什么

相同20条开发需求、相同模型和预算、相同数据及验收标准下，修复后的问询与交接流程让更多需求真正进入Core并完成交付。提升主要发生在Core之前：明确现有流程的完整能力，被问到时交齐当前题已有的销售事实。两处接线修复共同生效，不是单独prompt方法的因果增益，也不是Codex编程能力本身变强。

## 成本：成功变多，总消耗也更高

| 消耗 | 原始20题 | 修复后完整20题 |

| 根用量报告完整性 | 55/55 | 60/60 |
| 输入token | 2363188 | 6627856 |
| 其中缓存，包含在输入中 | 1311360 | 5281664 |
| 输出token | 38727 | 138263 |
| 整批墙钟，含最终检查 | 1039.87秒，17分20秒 | 2485.02秒，41分25秒 |
| 成功任务耗时中位数 | 264.17秒（3题） | 231.38秒（19题） |

总调用增加5次：意图调用从52降到41，但真正构建从3增到19。原来大部分题提前退出，这次多做了16个应用的构建与最终测试，因此不能说这次整体更省钱、更快。两批成功任务集合不同，缓存情况也不同，成功中位数不作为稳定加速证据。缓存是输入token的子集，不能重复相加；CLI登录没有逐题货币账单，人民币成本未知，根用量也不保证包含全部原生子Agent消耗。两批均未记录大于90秒的运行心跳间隙。

每个已进入Core的本次任务使用1次父级Core调用；父级返工计0。原生CLI内部可能自测、修复或使用子Agent，不能据此称“完全零返工”。

## 唯一未交付：191卡在澄清，不是Core做错页面

模型看到了两种税额描述：一处写“含税金额减已显示未税小计”，另一处要求独立四舍五入。模型请求确认口径；模拟销售的pricing主题已回答过，后续没有响应这个确认问题，而是返回“请具体询问……不要猜测”。三次意图调用用完，评测保留未交付；产品网页实际仍是“等待补充”，不是Core运行报错。

对本题固定6%税率、两位单价、整数数量的只读核算表明，两种税额计算数值等价：未税为50N/53分，税为3N/53分，不会出现恰好半分的舍入点，53个余数类均一致。因此目前不能说数值答案错误；问题是对两种文字表述的澄清闭环没有完成。没有调用Core，没有发布，也没有发布后功能缺陷。原输入、标准、对话和失败结果不改，不在本批新增修复重跑。见[单题诊断](191-rounding-diagnosis.json)。
