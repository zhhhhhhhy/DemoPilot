# 追加完整信息组：怎样区分信息与处理方式

目的：在原A一句话、B先问再整理之外，加入C完整业务规则直接交给Core，判断已有提升是否主要来自获得了缺失事实。

|组|Core收到什么|调用意图模型吗|
|---|---|---|
|A（保留原成绩）|原话和普通样例|否|
|B（保留原成绩）|原话、实际问到的销售回答、模型整理的目标/必须功能/验收|是|
|C（本轮新增）|原话后直接附上全部原始销售规则，其他字段与A相同|否|

完整规则采用每题预先固定的seller-answers文本，按原顺序拼接；不复制B输出、不加人工提炼、私有验收输入或预期金额。C只改变A的evaluation_intent字段；相同的通用工程处理仍由原Core执行。

十题全部运行C：四条原开发题单列，六条原保留题作为三组主表。所有输入在调用前冻结，之后不按C结果调整提示或规则。新组是知道原A/B结果之后追加的对照，旧保留题对本轮设计已非全新未知数据；不能称同期随机三组实验或新的盲测。

模型gpt-6.1-sol，reasoning medium，Core每次CLI配置300秒、最多2次返工、最多2题并行，使用原Core、普通testdata、工程门和独立数值/浏览器检查程序。B额外的询问调用单独计入总成本，C不为凑相同总调用次数浪费调用。

所有C任务到终态之后，执行全部112条既定浏览器检查，其中主表六题68条。评分后不反馈、不修复、不替换失败。原A/B文件及六题主审计哈希不变；未交付、无法确认、守卫误报等保留原状态并解释。

解释方式：A对C显示补足信息后能否做对；C对B显示同样业务信息之外，意图问询与整理整体是否还有观察到的额外收益。仍然是单次、少量、模拟销售任务，不能隔离每一句提示、自动询问体验或真实销售满意度。

重点防止误解：B08原评分的超时保留，不因诊断成功改为通过；A10长停顿不作效率比较；C的明确规则是实验者预先提供，不能声称C具备主动找出缺失信息的能力。

运行入口：scripts/run_quotation_full_rules.py（freeze / real / audit），报告入口：scripts/report_quotation_three_arms.py。历史源文件与新适配器均保存哈希和快照。
