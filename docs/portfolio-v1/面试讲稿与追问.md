# DemoPilot 面试讲稿与追问

## 30 秒项目介绍

我做了一个售前Demo生成系统，解决销售一句话缺少业务规则、Agent容易偏离需求的问题。我负责主动追问、上下文传递、Core迭代与独立验收。基于公开报价规则构建10条模拟需求，4条开发、6条保留；原话完整通过1/6，追问后5/6，追加完整规则直输对照也能做好功能，因此贡献主要是自动补齐缺失信息，尚未证明意图整理有额外准确率收益。

## 2 分钟项目介绍

DemoPilot 针对售前做 Demo 的过程。销售往往只说“演示采购审批”，但没有讲清供应商、审批理由和状态规则，直接生成容易偏离真实目的。

我把目标架构收敛为意图获取、Core 迭代和前端展示。Core 通过独立 Harness 调用 Codex CLI，后续可以替换执行框架。意图问询目前先在实验链路验证，产品表单仍人工确认。

我的重点是完成条件。每次生成后，子智能体运行静态探针，受信程序再用真实浏览器操作页面；失败就回到 Core 修复。通过后进入隐藏候选，再用全新浏览器状态复查，最后才能发布。每轮对话、代码、测试和截图都会保留。

我构建了 20 个分层案例，首批通过 15 个，定位 5 个失败后逐例修复复测通过。这个成绩只针对当时的已知契约。进一步做独立业务复查后，我发现计算正确不代表展示要求齐全，因此把三类场景的检查从 5 条扩展到 24 条。新门禁拦住了不符合新规的旧产物；补全输入后新生成的 3 例，24 条独立业务检查全部通过。

后端使用FastAPI和asyncio，包含状态持久化、取消恢复、SSE同步与日志指标。我还复现并修复了CLI输出管道导致持续等待的问题。此前三题意图试验未证明收益，原评分保留。随后聚焦报价，构建10题并固定4/6开发与保留，私有业务评分不回送Core。六条主比较中，原话完整通过1/6，主动追问整理5/6；追加“原话加全部规则、不走意图模型”后，68条功能操作全部通过，但读取检查误报一题，完整评分仍保留5/6。这让我把贡献定位在自动获得并可靠传递缺失规则，配合独立验收，而不把收益归功于提示措辞或基础模型能力增强。模拟销售和单次追加对照还不代表真实商业收益。

## 5 分钟展开顺序

1. 用“采购审批”说明为什么一句话会遗漏关键业务规则，以及怎样追问。
2. 画三模块架构，再展开 Core 内部的生成、测试、修复和发布状态。
3. 选一个真实失败例子：补货页面一度功能正确，但修静态安全后又引入 fetch，离线运行失败；说明为什么必须修复后重跑完整路径。
4. 主讲报价05：销售要求VIP优先，直接组自行选择规则得到570元，实际追问后得到指定的540元。用6条保留题1→5说明效果，同时说明模拟销售、小样本和11次额外调用；历史故障恢复数字分开解释。
5. 解释后端取消/超时问题、只读指标和适用边界，再介绍当前意图问询实验结果。

## 高频追问与回答

### 你的贡献是什么，哪些来自模型？

我的贡献是决定产品应该解决什么、怎么组织链路、哪些状态允许展示，以及怎样用对照和真实操作评价结果。Codex 帮助编写和修改代码，我负责审查与验收。我能够沿一个任务解释从输入到状态保存、CLI 执行、测试失败、返工和发布的完整过程，不把基础模型能力说成自己的算法。

### 为什么需要意图询问？一个好 prompt 不够吗？

prompt 可以把已有信息表达清楚，但无法凭空知道销售没有给出的业务细节。比如“折扣怎么计算”和“驳回后能不能继续下单”应当先问销售。这个假设需要通过最终业务结果来验证，所以我把“同样信息如何组织”的 prompt 实验和“询问是否获得了缺失信息”的意图实验分开。

### 新报价实验能证明什么？

这次六题完整条件评分是原话1/6、主动追问整理5/6、完整规则直输5/6；功能操作是36/68、67/68、68/68。B剩一条操作超时，C剩一条说明链接触发读取误报，均不改原分。五个信息不完整题的B/C业务规则文字相同，C没有意图整理仍做对了指定功能，所以本轮支持补全信息的价值，未显示整理步骤带来额外最终通过收益。样本少，C是后来追加，不能作总体因果或真实客户收益主张。完整[三组报告](../quotation-information-ablation-v1/结果与简历贡献.md)和[540元案例](../quotation-intent-v1/案例说明.md)可核查。

### 那主动询问还有什么价值？

完整规则组的答案由实验者预先写好，现实使用者未必一开始就说全。主动询问的工程价值是找出影响结果的缺口、向使用者索取信息，再完整交给Core；这次不是证明模型凭空理解了销售心里的规则。真人问答的产品页面和人工准备规则的工时尚未验证。

### 完整规则组18次调用，是否比询问组25次更省事？

只能说外层模型调用少7次，不能说人的总投入更少。C预先写完整规则的人工时间没有计入；它的3次内部返工都在补齐验收子进程执行证据，页面字节没变，不能当成3次业务逻辑修错。没有稳定降低返工、真实计费或人工工时收益的结论。

### 为什么需要两次浏览器检查？

第一次检查生成工作区，第二次检查实际准备交付的候选文件，并使用全新的浏览器状态，避免依赖第一次操作留下的状态。两道检查都通过才发布。离线评测还会对最终发布页做不反馈给 Builder 的业务复核，用来发现已发布结果是否仍有缺陷。

### 子智能体能决定发布吗？

不能。它实际运行只读静态探针并留下命令退出记录，模型自己说通过没有效力。真实页面行为由父进程的 Chromium 验证，状态由后端程序控制；当前 Core 没有主观打分的独立 Reviewer。

### 中间失败是否说明任务失败？

如果 Core 自己在预算内修复、最终发布并通过独立复核，就记为成功和一次或多次返工。最终没有完成才算任务失败。CLI 连不上、测试环境异常和页面业务错误也要分开标注，否则容易把环境故障误当模型能力上限。

### 你写的 100% 是怎么来的？

首批 20 例通过 15 例；我针对 5 个失败案例逐个修复和复测，最终这些案例也通过，所以是增量合并的 20/20。它不是修复后同一代码版本一次跑完 20 例，更不是生产成功率。若简历篇幅不够解释，我会只写“定位并修复 5 个失败样本，复测 5/5 通过”。

### 返工减少 80% 可以证明 prompt 有用吗？

它是 4 对案例里返工 5→1 的观察，两组最终发布都是 4/4。因为样本少且旧组先跑，不能作强因果结论，也不能据此声称意图识别提高了最终成功率。要作更强结论，需要独立销售场景、交错顺序与多次重复。

### 任务是怎么持久化和恢复的？

后端保存任务状态、事件序号、检查结果和工作目录，使用临时文件替换原记录，避免半写文件。评测 runner 恢复时先检查终态，只补结果而不重复生成；产品 API 显式 resume 会重新调度失败任务，不能声称每步都已做到原生断点续跑。SSE 返回完整状态快照，重连后重取当前状态，目前没有服务器增量事件重放。运行任务由进程内 asyncio 调度，所以多 worker 共享同一目录不是当前支持的部署方式。

### 最实际的一个后端问题是什么？

Windows 的 CLI 外层进程退出后，子进程可能仍持有输出管道。如果只给等待进程设置超时，随后读取输出可能一直不结束；如果收尾时又调用 communicate，还可能和正在读取输出的协程冲突。我把超时覆盖到整个会话，让输出只有一个读取者，取消时终止进程树并保存已有日志，并为这条路径加入回归验证。

### token 和耗时怎么统计，能算成本吗？

从 CLI 保留的完成事件读取它报告的 token，按实际子会话累计，意图和 Core 分开统计。没有 token 的失败会话保持未知，不当作零；没有真实账单和单价就不报金额。耗时是本地实验端到端与持久化记录的时间，不声称线上 SLA。

### 文件权限是不是强隔离？

目前是独立工作目录、CLI 权限策略、prompt 中允许写入的目录、输入哈希和结束后的路径审计。它能在本项目门禁中发现越权修改，但不能当作面对恶意代码的容器隔离。多人服务下一步需要独立容器、独立身份和资源配额。

### 为什么不用数据库、Redis 或消息队列？

当前定位是本地单用户 MVP，文件记录已经能够支撑恢复和审计。我先验证生成与验收闭环，再根据需求引入更复杂的组件。如果多人同时运行，下一步是数据库状态机与幂等键、独立 worker 队列和任务租约，不能只把 asyncio 并发数调大。

### 你怎么验证没有为了过测试而硬编码？

预期结果和 gold 不放进模型输入，两个实验分支使用相同普通 fixture，独立审计使用多条样例和边界操作。仍要承认模型看到了控件和操作协议，测试反馈也会帮助它修复，所以已知契约通过不等于对所有业务情况泛化。

### 项目最大的不足是什么？

数据集仍以人工编写的演示场景为主，困难集的业务语义有通用化问题；真实销售访谈、更多独立场景和线上使用数据都不充分。我的后续目标是先验证意图获取对最终业务结果的帮助，再试点销售制作时长，而不是凭空加用户数和性能数字。

## 现场演示步骤

先展示一个销售输入及对应的询问、回答，再展示同一 run 的 Core 过程、某次测试失败和后续修复，最后打开已发布页面操作两条不同数据。若展示意图效果对比，必须使用《指标与实验报告》列出的同一批次 A/B 结果；不要拿旧完整流水线的演示总数冒充本次成绩。

## 面试准备是否完成的自查

- 不看讲稿，能在 2 分钟内说清业务目的、三项贡献和一个有口径限制的结果。
- 能画出意图、Core、展示，以及 Core 内部的检查与返工位置，说明独立评分为什么不能反馈后再覆盖原分数。
- 能打开一个 run，把失败、修复和最终结果对应起来，解释中间返工与最终失败的区别。
- 能解释 15/20、增量 20/20、4 对 prompt 试验和意图询问试验各自是什么，不混用分母。
- 能打开上述关键函数讲清输入、状态改变、异常路径和当前局限，而不是只背架构名词。

材料和证据准备完成，不等于已经验证本人现场表达能力。建议按这些问题录一次 2 分钟介绍，再根据事实核查遗漏和夸大之处。
