### 逐例结果与原因

| 案例 | A | B | 具体原因与环节 |
|---|---|---|---|
| 报价 | 已发布，业务复查未通过 | 意图未交付，未生成 | A 的 8 组金额正确，但小计/折扣明细标签未全显示；B 在两轮后仍询问币种和计价周期，未达到 ready。前者是发布检查覆盖不足，后者是两轮问答/冻结回答下的意图交付失败。 |
| 线索跟进 | 业务复查通过 | 已发布，冻结审计未通过 | B 保留了任务数据，但按当前线索过滤显示；审计要求切换后仍能看到全局历史。它不等于任务数据丢失，暴露了原需求与审计展示约定的不充分澄清。 |
| 采购审批 | 已发布，业务复查未通过 | 已发布，业务结果未能确认 | A 没有指定 A/B/C 供应商；B 已显示三家，但冻结审计不能通过原生选择框或每行按钮建立对 B 的可观察选择，不能判通过，也不能直接断言所有功能错误。 |

**结论：这轮没有证明当前意图询问提高最终业务通过率，也没有减少返工。** 结果受两轮问答预算、回答脚本完整性、可观察 UI 约定和三例开发数据限制，不能当作真人销售意图识别准确率。问题不应笼统归为 Codex 能力不足：问询终止规则、输入中的业务含义、验收覆盖与测量可观察性都需要改进。

## 从失败到改进

| 发现的问题 | 本轮动作 | 怎样验证 |
|---|---|---|
| CLI 外层退出后输出读取仍可持续等待 | 将截止时间覆盖整个会话，移除竞争读取，超时/取消后有限收尾并保留中途输出 | 真实子进程超时、取消、退出后不关闭管道三项回归；真实 CLI 与新发布任务；`evidence/lifecycle-before-after.json` |
| 难以区分耗时、返工、调用与未知 token | 新增只读 `/api/runs/{run_id}/metrics` 与证据收集器 | 新版真实 HTTP 样例返回两次 Core 调用、0 返工和约 240 秒；缺失 usage 不填零；`evidence/live-api-metrics.json` |
| 发布契约没有覆盖全部业务目标 | 新建 sales-business-v2，保留旧数据；将完整 9/4/11 条路径纳入 Core 发布前与候选复核 | 用新目录由真实 CLI 重新生成三个 Demo，再用同一独立业务审计验收 |
| 跟进展示范围和供应商操作方式有歧义 | 新规格明确全局任务历史、原生供应商选择和可见选择结果 | 这是规格澄清与覆盖改进的联合干预，不是假装只改一个 prompt 的严格 A/B |

新版覆盖目标为 3 个案例、24 条路径。Core 自己生成并修复页面，根助手没有手动修改生成的 HTML/CSS/JS；它们是已知失败后的定向回归，不能混入原 A/B 分子，也不是新的独立测试集。

新版运行结果和独立审计保存在 `evaluation_sets/sales-business-v2/results/20261016/`，最终回归结果单独记录在本报告末节。

## 个人贡献与简历口径

本阶段已能支撑：需求与验收定义、可插拔 Core 执行、后端会话可靠性、受控发布、分层评测与失败归因。可以讲历史 5 例修复与当前验收覆盖改进；不能把意图提升作为已取得成绩。

验证材料包含 30 项针对性检查、1 项终态恢复检查、1 项新版覆盖检查及 2 项真实浏览器选择器回归，共 34 项通过；这些回归中有模拟数据，也有真实进程与真实 HTTP。它们证明对应工程路径，不代替 CLI 生成质量或真实客户收益。

下一层目标是补问真正影响交付的业务含义，将非阻断演示细节与必须确认的规则分开，再把问询接入真人销售页面，并在至少 20 对独立需求上评估完整结果与总成本。本阶段没有测量生产用户、转化率、销售工时节省或分布式吞吐。

## 联合改进后的定向回归结果

本节是在原 A/B 评分后，补全业务上下文与发布前检查的另一轮试验。输入已明确，Core 没有重新调用意图询问，不能把这个结果归因于意图模块。记录中的 `coverage-repaired` 才是本节分组，继承的请求 profile 标签不代表实际调用了意图 Agent。

| 新生成场景 | 新 Core 检查路径 | Core 返工 | CLI 调用 | 独立业务复验 |
|---|---:|---:|---:|---|
| 报价 | 9 | 0 | 2 | 9/9 通过 |
| 全局线索跟进 | 4 | 0 | 2 | 4/4 通过 |
| 采购审批 | 11 | 1 | 4 | 11/11 通过 |
| 合计 | **24** | **1** | **8** | **3/3 场景，24/24 路径通过** |

采购的内部返工主要用于对齐固定 UI 提示文案，如“不能回退”和契约中的“不可回退”；这不等价于状态回退逻辑全部错误，仍按实际返工记录统计。三页均由真实 CLI 生成，原始 A/B 页面与评分保留，没有在独立评分后手工修改页面。

新门禁还对三个保留的旧产物进行负向验证，三个均被拒绝，原文件哈希未变化。其中线索样本对应新明确的全局列表要求，不把旧的按线索过滤说成已证实数据丢失。

验收器另有一项后端优化：此前遇到选项值 `L-02`、显示标签为中文时，先尝试不存在的标签会固定等待 5 秒。相同真实浏览器样例，修复前 **5.192 秒**，修复后 **0.547 秒**；另验证标签优先语义保持不变。随后将全部三页的 24 条路径在新验收器下重新执行，24/24 通过，原卡片未改、模型调用为零。这是一个控件路径的实测，不是整个系统提速十倍或线上 SLA。

这个改进支持的简历表述是：发现已发布结果与完整业务要求之间的覆盖缺口，将三类场景从原来的 5 条契约路径扩展到 24 条，加入明确输入与可观察结果后，新生成的 3 例全部通过全量独立复验。它是已知样本的联合修复回归，不能替代独立新数据的效果评估。
