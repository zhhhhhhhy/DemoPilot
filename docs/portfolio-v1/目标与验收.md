# DemoPilot：面向简历与面试的建设目标

> 当前任务已收敛为报价专项：10条有公开来源的需求、4条开发与6条保留、两组真实生成及全量独立验收。结果为1/6对5/6，见[本轮结果](../quotation-intent-v1/结果与贡献.md)。下文“三对”“至少20对、18/20”是历史阶段和未来设想，不是本轮目标或已经取得的成绩。

## 最终目的

让销售从一句不完整的需求出发，得到一个符合其业务意图、可以现场操作的售前 Demo；让开发者可以解释每次生成为什么成功、为什么失败、一次改进到底改变了什么。

本阶段交付的是本地静态演示系统。客户转化率、真实售前工时节约、生产用户量没有现场数据，不能作为现有成绩。

## 核心产品链路

销售一句话 → 意图模块询问缺失细节并形成确认后的目标 → Core Builder 调用 Codex CLI 生成、测试、修复 → 通过后进入展示区。Core 内部的子智能体验收和程序验收负责返工；面向最终结果的独立浏览器复核只用于评测，不能在评分后暗中替 Builder 修复。

## 个人贡献的组织方式

| 贡献 | 解决的问题 | 工程产出 | 如何证明 |
|---|---|---|---|
| 需求获取与目标构造 | 一句话省略计算、状态和展示规则，生成内容容易偏离销售目的 | 原始话术、追问、销售回答、确认目标的独立记录；A/B runner | 同一初始话术在有无询问两条路径下比较最终业务结果，包含询问成本 |
| 可迭代的 Core 与 Harness 接口 | 一次生成难以完成所有目标，后续需要替换执行框架 | 统一 build/acceptance 接口、隔离运行目录、测试反馈、有限返工 | 真实 CLI 回合、每次失败、修复次数和最终状态可追溯 |
| 可靠的后端任务执行 | 子进程超时、取消或重启后可能失去进度、重复执行、误报完成 | 异步任务管理、原子状态保存、SSE 状态同步、子进程收尾、运行指标 | 真实子进程回归、API 路径与拒绝非法操作的验证、记录重读 |
| 可验证的发布与评测 | 页面看起来能用不等于完整实现业务功能 | 固定测试数据、程序浏览器验收、隐藏候选、发布门禁、独立复核 | 对全部 fixture 实际操作；只给通过结果发布；失败保留分母 |

参考项目和 AI 生成代码是实现基础。面试中应突出本人提出的目标、架构取舍、验收定义、失败分析和改进决策，并如实说明 AI 辅助实现；不能把基础模型能力或上游代码归为个人算法发明。

## 本次交付与验收

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| 1. 核实项目 | 架构、贡献表、历史指标核验 | 每个可写入简历的数字能从现有结果文件重新计算；区分单批运行与增量补测 |
| 2. 修复执行可靠性 | CLI 超时/取消修复与窄范围回归 | 超时覆盖进程及输出读取；没有并发读取冲突；取消终止进程；中途日志留存 |
| 3. 补后端指标 | 每次运行耗时、调用数、token、返工、失败环节的只读统计 | 正常与失败记录可重算；缺失值不记零；相同日志不重复计费 |
| 4. 有效意图试验 | 3 个难度案例、共 6 个真实分支及独立业务审计 | 初始话术相同、模型/预算/fixture 相同、答案在提问后释放；全分母、全量 fixture、无评分后修复 |
| 5. 面试材料 | 简历 3 条、30 秒与 2 分钟介绍、架构讲解、常见追问与代码入口 | 每个贡献包含问题、方法、结果；没有未经验证的提升或并发规模；面试可以沿证据文件追溯 |

实验结果可能是提升、持平或下降，三者都属于有价值的结果。验收要求比较有效，不要求制造有利数字。若调用服务持续失败，则完成诊断与可独立交付的材料，并将效果实验明确列为未完成，不能以“工程状态 completed”替代用户目标。

## 指标定义

- 最终业务通过率：发布成功且独立浏览器完整业务检查通过的案例数 / 本组全部计划案例数。终态失败、调用失败和未发布均保留分母。
- 首次通过率：无需 Core 返工且最终业务通过的案例数 / 全部计划案例数。
- Core 返工：第一次生成之后，Core 自己执行的修复轮数；不是外部审计后替它修改。
- 调用成本：意图模块 + Builder + 验收子进程分别计数，并报告 CLI 日志里可见的 token；没有单价和账单证据不推算费用。
- 耗时：端到端耗时与各 CLI 子会话耗时；它们是本地实验耗时，不是线上 SLA。
- 失败环节：意图获取、Core 功能、执行基础设施、验收/测量、最终已发布缺陷。中间失败后自行修复成功只记返工，不算最终任务失败。

## 后续路线与停止条件

第一层交付是能演示、能复核、能讲清的个人项目。当前 3 对试验只能作小样本观察；若要把“意图模块提升成功率”作为简历主数字，下一层应冻结更多彼此独立的销售场景、保留未参与调试的案例、交错顺序并重复运行，报告完整分母与不确定性。

下一层的具体实验产出是：至少 20 对独立初始销售描述，按简单/中等/困难 10/5/5 分层；当前 3 个开发案例只用于调试；A/B 顺序交错，所有分支使用正常且一致的生成与修复预算。希望意图组至少有 18/20 最终业务通过，且相对直接生成能提高通过率或减少返工。18/20 是拟定的本地验收目标，不是已取得成绩；若未达到，就报告差距与失败原因。

若最终通过率相同，也可以证明成本或首次通过的改善，但必须把询问本身的调用、token 和耗时加入比较。只有独立数据和重复结果足以支持时，才将它升级为简历中的效果主张。

下一层产品交付还应将当前实验 runner 中的意图会话接入 API 和前端，允许真人销售回答、确认并启动 Core；验收为原始一句话到发布页的真实浏览器全流程。当前表单中的人工确认不能算作已接入自动询问。

再下一层才是试点真实销售：由销售确认业务目标并记录人工制作时长，与 DemoPilot 用时和修改次数比较。没有这层数据前，材料仅声称技术评测效果。

队列/数据库、多租户、容器隔离和多机扩展应由实际并发与安全需求触发；本次不为了简历罗列技术栈。当前文件存储、进程内调度的适用边界必须在面试材料中明确。
