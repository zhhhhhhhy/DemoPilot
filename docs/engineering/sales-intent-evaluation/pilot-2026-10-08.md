# Sales intent downstream pilot（2026-10-08）

这次实验评估的是“销售原始话术是否经过当前的人工确认意图表单”对最终 Demo 的影响。两组都使用真实 Codex CLI、同一 Core Builder、同一测试数据、同一 Chromium 验收和同一发布后全新浏览器复核。

需要先说明边界：当前产品的意图模块不是 AI 访谈器。销售在前端填写场景、用户、must-have、验收和约束后勾选确认，后端只用 `build_intent_statement()` 做确定性拼装。因此这轮没有测 AI 意图识别准确率，只测“原始话术直达 Core”和“人工确认的结构化意图交给 Core”的下游差异。

## 结果

| 指标 | 原始话术直达 Core | 人工确认结构化意图 |
| --- | ---: | ---: |
| 最终发布 | 3/3 | 3/3 |
| 浏览器业务契约通过 | 3/3 | 3/3 |
| 发布后全新浏览器复核 | 3/3 | 3/3 |
| Core 返工总轮数 | 2 | 2 |
| 平均返工轮数 | 0.67 | 0.67 |
| Codex CLI 调用次数 | 10 | 10 |
| 意图识别准确率 | 未测量 | 未测量 |

逐个用例的结果也完全一致：

- 套餐报价卡：两组首轮发布，报价的 3 席和 4 席结果都通过浏览器检查。
- 销售线索跟进台：两组首轮发布，行业筛选、线索详情、负责人和任务创建都通过。
- 采购审批协同台：两组都经历 2 次返工后发布，主流程、越序阻断和退回分支都通过。

## 这个结果说明什么

在这 3 个销售场景中，人工确认的结构化意图没有提高最终发布率，也没有减少返工。原因不是已经证明“意图模块没有价值”，而是当前 Core 拿到了完整的浏览器验收契约和本地测试数据；这些确定性门禁已经给了 Builder 很强的实现约束。简单和中等场景即使不提供结构化 must-have，也能通过；困难采购场景两组都需要返工。

因此目前不能报告“意图模块让最终准确率从 X 提升到 Y”。本轮的“3/3 发布”只能叫工程发布可靠性；它不是销售意图语义准确率，也不是真实 CRM、库存、报价系统的业务准确率。现有发票和销售验收主要检查浏览器可见状态，不能替代真实业务金标准。

## 流程和失败边界

六个真实后端运行全部进入 `completed + published`，浏览器和发布后复核全部通过。原始采集器在最后一个确认组困难用例上达到 1800 秒等待上限，先退出并没有写出汇总文件；这是测量/采集失败，不是产品失败。之后根据六个已落盘的终态 `run_id` 只读补采集，生成最终报告。

## 要真正评测“意图识别准确率”还缺什么

需要增加一条真实链路：

`raw_sales_brief → AI 意图获取/追问 → typed_intent → Core Builder → 隐藏业务 gold 验收 → 发布`

每个销售 brief 需要人工标注 actor、问题、目标、实体、must-have、流程顺序、约束、非目标和预期业务结果。然后分别报告：

1. 意图层：字段 Precision/Recall/F1、流程顺序准确率、约束违规率。
2. Demo 层：隐藏业务 gold 的输出/状态正确率、关键需求覆盖率。
3. 发布层：published rate、首轮通过率、返工次数、浏览器和发布后复核。

只有三层同时达到阈值，才能称为“销售意图到最终 Demo 的端到端成功”。
