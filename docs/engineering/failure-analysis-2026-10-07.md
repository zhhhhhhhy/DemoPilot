# Codex CLI Core Evaluation Failure Analysis

Date: 2026-10-07  
Baseline: `evaluation_sets/codex-cli-v1/results/full-real-post-audit-20261006.json`  
Scope: the five cases that ended `cannot_complete` in the 20-case real run.

## Record audit

The project already retained raw evidence for every failed run: `run.json`, three iteration prompts, CLI JSONL transcripts, stderr logs, acceptance records, event history, and browser screenshots where Chromium reached the page. That evidence is sufficient for reconstruction, but it was not sufficient as a stakeholder-facing record because no single file connected the baseline symptom, repair action, and measured after-result for all five cases. This document fills that gap. The machine-readable companion is `failure-analysis-2026-10-07.json`.

The trusted `acceptance.json` generated by DemoPilot is the final authority. A Core Builder message, a child-agent message, or a local command that the trusted harness did not record as passed is not counted as an improvement.

## Per-case iteration evidence

### `simple-receipt-summary-01` — CLI transport blocked generation

- **Before:** The Builder never reached a usable card. Iteration 0 contained connection/TLS failures; iterations 1 and 2 ended with `workspace routing discovery failed`.
- **Action attempted:** The loop preserved the failure, launched the read-only acceptance child where possible, and retried the Builder for all three allowed iterations.
- **After:** No product behavior was measured. `card-web` was missing, the child acceptance command did not pass, and the case stayed hidden. This is a Harness/CLI failure, not evidence that the receipt UI logic is defective.
- **Evidence:** `.data/runs/b1c719b74fb3/run.json`; `.data/runs/b1c719b74fb3/artifacts/evidence/core/iteration-{0,1,2}/`.

### `simple-appointment-card-01` — CLI workspace routing blocked generation

- **Before:** All three Builder attempts failed during Codex CLI workspace routing before producing a testable card.
- **Action attempted:** The loop retried three iterations and retained the CLI and child transcripts instead of publishing an empty workspace.
- **After:** No trusted browser result exists; the case is hidden as `cannot_complete`. It must be rerun after the CLI transport is healthy before any product-quality conclusion is made.
- **Evidence:** `.data/runs/1866980561b0/run.json`; `.data/runs/1866980561b0/artifacts/evidence/core/iteration-{0,1,2}/`.

### `medium-replenishment-01` — static safety repair regressed offline behavior

| Iteration | Before | Action | Trusted after-result |
|---|---|---|---|
| 0 | `fetch('../testdata/...')`, unsafe HTML injection; low-stock list missed `无线鼠标`; 2 console errors | Builder replaced network loading and unsafe rendering with embedded data/DOM APIs | The functional path was still failed; 4 issues remained |

The correct next method is an offline JavaScript constant in `app.js`, with no HTML data script and no runtime fetch.

## Cross-case diagnosis

There are two different failure populations:

1. **Harness/CLI availability:** the two simple cases failed before generation because Codex CLI could not establish workspace routing. Retrying the browser cannot repair these cases; the next measurement must first establish a healthy CLI transport and then rerun the same frozen cases.
2. **Builder repair regression:** the three generated cases reached Chromium. The common loop was `runtime fetch → inline JSON fixture → runtime fetch`. The prompt said to use local testdata but did not give an explicit offline implementation pattern. Under `file://`, fetch produced console errors; when the Builder moved data into an HTML script block, the static scanner rejected it; when it moved data back to `fetch`, the browser behavior regressed.

## Targeted action for the next iteration

The Core Builder prompt now explicitly requires:

- copy the needed fixture values into a JSON-serializable constant in `card-web/app.js`;
- never use `fetch`, XHR, WebSocket, imports, service workers, or any runtime file/network read;
- allow one external `app.js` script only; forbid HTML inline scripts and inline event attributes;
- bind events with `addEventListener` and render through DOM APIs;
- after a safety edit, rerun the complete authored browser contract and preserve a previously passing state machine.

The five failed cases were rerun through the real Codex CLI with separate output files. Their terminal results are recorded in the machine-readable companion and compared case by case. A transport failure remains `unverified/blocked`; only a terminal published case with a passing fresh post-publish audit counts as a recovered case.
