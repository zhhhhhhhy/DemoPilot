# 历史修复通用性审查

审查日期：2026-10-20。代码基点：`a32dba2c60097aae904f010763b7995b9fa8cc88`。本次盘点24个Git提交，重点检查下表10组关键修复；并非逐行证明全部历史模块没有问题。工程账本：`TX-dc0a599ec621`。

## 结论

**部分修复仍依赖已见样例的表达和主题，没有把整类问题变成可检查的工程约束。** 最明确的位置是模拟销售的信息交付、意图与Core之间的能力说明，以及验收覆盖。所审业务模块与关键差异未发现按最终题号写答案或直接放行，但这不能推出修复已经具备通用性。

CLI进程、端口独占、权限和发布事务等修复具有通用机制；关键词补答、一次主题复述等修复属于窄规则补丁。应分别评价。下面所称样例依赖是工程鲁棒性风险，本次没有训练模型或估计统计意义的训练/测试过拟合程度。

本次不修改产品、提示、数据、验收标准或正式结果；0次模型调用、0次浏览器重跑、0条最终题重测。已完成的最终题仍为 **13/15**，另外 **85条未执行**。本报告中的建议均未实施。

## 2. 问答工程遗漏：没有明确的问题—事实合同

当前问题输出是字符串列表，答题器按词查找topic。`answers_for`没有收到结构化的缺失字段、已知字段、冲突字段或逐字段来源，只能猜这段文字是在问什么。

证据：[字符串问题结构](../../../backend/src/demopilot/sales_contract.py#L272)、[关键词与一次性主题补答](../../../scripts/run_sales_benchmark_pilot.py#L57)、[数据中的固定别名](../../../scripts/sales_benchmark_data.py#L376)。

开发事实上的零模型检查如下。题目事实来自原60条开发需求；手工构造四类各8种表达，其中2种含既有关键词、6种用不同说法表达相同取信息目的。没有使用未测最终题构造探针。

| 要取的信息 | 含既有关键词的问法 | 手写同义改写 | 观察 |
| --- | --- | --- | --- |
| 商品目录 | 2/2触发目录回答 | 0/6触发目录回答 | “产品价格”能答，“各款货品多少钱”漏答 |
| 定价方法 | 2/2触发定价回答 | 0/6触发定价回答 | “定价规则”能答，“金额的计算办法”漏答 |
| 审批角色与顺序 | 2/2触发流程回答 | 0/6触发流程回答 | “审批流程”能答，“报批要经过哪些岗位”漏答 |
| 配送费用 | 2/2触发配送回答 | 0/6触发配送回答 | “运费”能答，“送货要付多少钱”漏答 |
| **不同问法合计** | **8/8** | **0/24** | 两个历史版本与当前版本具有相同缺口 |

`5c7acb6`、`894690f`及当前版本都运行了相同32种问法的纯函数检查；历史增加复述规则没有改变该结果。60组开发事实上的1920次检查重复使用相同别名，不应包装成1920个独立需求。上述表达故意对照关键词，不是随机抽样；**不能写成实际销售或LLM意图准确率为0/24**。它证明的是当前模拟销售无法稳健承接不同措辞。

多轮检查还发现：首次定价回答及第一次明确复述都交付，第二次复述不再交付定价；不含指定复述词的“请再解释一下定价规则，仍不清楚”也不交付。问题里只要出现“确认”，还会触发workflow别名，给询问价格的人额外返回审批资料。既有单测把第二次澄清不再回答写为预期，未证明这种限制满足真实对话需要。证据：[现有重复主题测试](../../../backend/tests/test_sales_benchmark_protocol.py#L99)。

这是一组机制问题：漏交应答事实、混交其他主题、将topic已出现等同于用户已理解、没有回答后是否取得进展的检查。只增加“协议单价”一个词不能解决这些问题。

本次最初的诊断统计曾把“有任意主题回复”当成“定价已回复”，因混入审批回答而误计第二次定价复述；已保存v1并改为统计目标topic。该修正不改变任何原正式成绩，反而说明日志必须记录实际交付了什么字段，不能只记录有无一段文本。

## 3. 能力说明没有统一来源，导致同一类脱节再出现

过去含税问题是Core已经支持具体金额拆分步骤，而意图说明不完整；修复主要补写提示说明。本次进一步发现，**模拟日期初始值已在Core接口定义为2026-03-15，意图上下文却没有同一默认值**。

证据：[Core接口默认值](../../../backend/src/demopilot/sales_core.py#L31)、[意图提示组装](../../../backend/src/demopilot/sales_core.py#L229)、[意图能力说明](../../../backend/src/demopilot/sales_contract.py#L300)。意图请求只拼接INTAKE_INSTRUCTION、输出结构和对话；没有把UI_CONTRACT的默认值交给它。数据构造也直接复用UI_CONTRACT，见[构造代码](../../../scripts/sales_benchmark_data.py#L865)。

因此，对176仅说“模型多问一个非必填日期”不够准确。更深的遗漏是：字段属于销售必须确认、产品已有默认值、系统推导值，还是不支持的要求，系统没有共享且可检查的定义。这里应补充此前的原因解释，原失败记录和13/15分数仍保留。

另一个相关缺口是来源校验。当前只检查引文是否出现在用户文本，没有逐字段证明数值来自哪里。本次用一条开发需求构造一个错误加价方案，只引用原商品名：结构校验及相同的引文子串条件仍接受。**这是合成结构探针，不是实际模型幻觉或已发布错误页面；网页仍要求用户确认，评测的标准方案比较也会拒绝该改价。** 证据：[引文校验](../../../backend/src/demopilot/sales_core.py#L237)。

## 4. 验收工程遗漏：需求写了，但检查没有逐项对应

独立审查与主审复核确认两个静态覆盖缺口：

1. **切换报价后恢复表单输入。** 需求写了恢复原商品、数量等，但快照只检查金额、状态和计数；计算前，驱动又把表单填回参考记录的值。因此它没有直接证明切换后的输入恢复正确，且重填动作可能遮蔽该错误。证据：[快照](../../../backend/src/demopilot/quotation_contract.py#L139)、[输出字段](../../../backend/src/demopilot/quotation_browser.py#L91)、[计算前重填](../../../backend/src/demopilot/quotation_browser.py#L221)。
2. **可点击但被拒绝的操作应显示原因。** 接口要求错误说明，现有可见快照不读取#error；记录参考模型拒绝了操作，不等于实际页面向用户说明了原因。按钮直接禁用这一既有合法例外应保留，不要求被禁用按钮额外弹错。证据：[接口要求](../../../backend/src/demopilot/sales_core.py#L33)、[实际观察范围](../../../backend/src/demopilot/quotation_browser.py#L114)。

本次没有注入这两类页面错误或重跑浏览器，因此只能确认**检查未完整覆盖约定**，不能宣称13个页面实际存在这些缺陷。81条实际浏览器路径仍确实运行并通过，只应按其实际覆盖范围解释。

另外，公开和私有验收使用同一参考QuoteModel和流程生成器。新浏览器上下文提供了独立运行环境，私有数据也变换了取值与顺序，但这两次运行的答案不是分别独立推导的；共同漏掉的要求仍可能两次通过。证据：[流程生成](../../../backend/src/demopilot/quotation_contract.py#L247)、[验收编译](../../../backend/src/demopilot/quotation_contract.py#L459)。共享参考本身不是作弊。**项目此前已有字面手算校验和8类受控故障检查**，不能说这些手段从未做过；此次发现的是它们未覆盖表单恢复、拒绝说明等遗漏，尚未与每条必需行为逐项对应。原证据见[手算校验](../../quotation-reliability-v2/rule-calibration.json)、[受控故障脚本](../../../scripts/calibrate_quotation_reliability.py)。

早期hard-v2还存在难度叙述大于实际检查深度的问题：所谓阈值/角色分支只点击通用branch按钮、比对分支文字前8字，没有输入阈值两侧数值或真实角色条件。这说明多步骤演示不等于深入业务验收；证据：[早期分支检查](../../../scripts/materialize_hard_eval_v2.py#L199)。它与当前报价集是不同历史评测，不能混合成绩。

## 5. 为什么以前的提升不足以证明修复通用

- 原题恢复是必要的回归证据，不能替代换表达、拆成多轮、改变合法操作顺序和输入边界的检查。现有20/40题虽覆盖多个规则组合，仍由同一构造器生成；5变体主要改变金额和信息完整度，不是5名独立客户或5套独立语言风格。
- 原3/20→19/20同时包含产品意图说明和模拟销售信息交付改动；它证明整个链路更容易交付，不能单独归因为意图模块更聪明。原记录已说明联合修复，本次继续保留该边界。
- 40/40异常覆盖的是固定运行与安全故障配方，不保证自然语言问答稳健，也不保证遗漏的页面要求已被检查。
- 失败原因目前还要从自由文本和轨迹事后分析，缺少统一的字段级进展、模拟用户故障、能力上下文不一致、CLI故障与业务断言失败等类型记录。应同时保留端到端未交付分母与各层归因，不能删除评测器故障以修饰原总分。

## 6. 后续修复应达到的通用标准（尚未实施）

| 工程措施 | 应解决的一类问题 | 应如何验收 |
| --- | --- | --- |
| 问题、事实和来源按字段关联，保留自然语言展示 | 不靠几个汉字决定交付什么信息；已答事实可重复解释，冲突另列 | 不同表述指向同一字段时交付相同事实；不混交其他字段；拆轮次、重复询问、真冲突及未知字段均有预先写明的结果 |
| 共享能力与默认值清单，意图/Core/校验使用同一版本 | 避免意图误认为Core做不了，或追问已有产品默认值 | 每个字段标明销售必填、产品默认、推导或不支持；提示与接口版本不一致应在运行前被发现 |
| 需求—浏览器断言覆盖表，观察后再操作 | 避免驱动把页面错误修好，或有需求却没有断言 | 表单恢复和拒绝说明均直接读取；故意删除这两个功能时检查必须失败，正确实现通过；保留禁用按钮例外 |
| 固定一批独立改写、多轮和参数边界的开发检查 | 防止只对历史失败句子修到通过 | 修复先通过原失败，再通过未用于修改的表达/轮次/边界与负例；检查不按题号放行，不改题目规则 |
| 扩展既有手算校验和受控故障检查 | 发现共享参考实现和共用流程尚未覆盖的盲区 | 保留既有手算与8类受控故障，补齐本次恢复/错误说明等遗漏；按规则族增加关键边界，逐项证明缺陷能够检出 |
| 产品、模拟销售和判分器分别版本化并记录失败类型 | 避免把评测接线修好当模型能力增益 | 改动归属与成本可追溯；产品效果比较冻结其他部件；原13/15保留，新版本另记，已暴露15题不再称未见题 |

优先修复信息交付合同和共享能力说明，再补齐已有需求的漏检断言，并在开发数据上验证；之后再决定新的冻结评测。**本次没有修复这些缺口，也没有启动余下85条。**
