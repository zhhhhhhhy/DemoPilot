# Prompt A/B pilot（2026-10-08）

这次实验只回答一个问题：在 Codex CLI、测试数据、Core Builder 迭代规则、验收子智能体、独立 Chromium 和发布后复核都相同的情况下，结构化的 Intent/Goal Prompt 是否让生成过程少返工。

控制组只把场景、优先级和 must-have 能力交给 Builder；处理组额外给出 Intent、Goal、业务流程、预期结果、验收方式和数据集上下文。两组都保留同一套文件权限和确定性门禁，所以这不是“有验收”和“无验收”的比较。

## 结果

| 指标 | 控制组：control-legacy | 处理组：treatment-current |
| --- | ---: | ---: |
| 最终发布 | 4/4 | 4/4 |
| 最终 Chromium 验收 | 4/4 | 4/4 |
| 发布后全新浏览器复核 | 4/4 | 4/4 |
| 首轮通过（以 `revision_count=0` 计） | 0/4 | 3/4 |
| Core Builder 返工总轮数 | 5 | 1 |
| 平均返工轮数 | 1.25 | 0.25 |
| Codex CLI 调用次数 | 18 | 10 |

控制组每个 case 都至少经历了一次门禁触发的返工；中等发票复核台经历了两次。处理组只有发票文字识别台需要一次返工，其余三个 case 首轮通过。处理组的发票返工原因是页面没有引用 `testdata` 中的发票文件，修复后浏览器验收和发布后复核均通过。

## 失败出现在哪个环节

有效 pilot 没有最终 Builder 失败，也没有发布失败。控制组的失败都出现在候选产物交给验收门禁之后：Chromium 状态不满足验收契约，或验收子智能体没有留下可复核证据，系统因此把任务送回 Core Builder。处理组的发票 case 也是验收门禁发现问题后返工。CLI 超时属于中间过程事件；只有它进一步造成验收或发布不通过时，才增加返工轮数。

这说明当前项目的难点不是“页面能不能生成出来”，而是生成的候选页面能否留下真实、可复核、与 `testdata` 对齐的交互证据。现有 loop 能把这些问题拦住并修复，所以最后两组都能发布；这不等于一开始就没有问题，也不等于 Prompt 已经被证明完美。

## 结论边界

这个 4 对 pilot 支持“结构化 Prompt 可能减少返工”的初步信号：返工从 5 轮降到 1 轮，下降 80%；首轮通过从 0/4 变成 3/4。最终发布率两组都是 4/4，因此不能声称 Prompt 提高了最终成功率。

本轮先跑完控制组，再跑处理组，且只有 4 个配对 case，所以还不能作无偏因果结论。正式评测应在全部 20 个 case 上随机交错运行两组，并保持同一 provider、超时、最大迭代次数、工作区隔离和验收门禁。
